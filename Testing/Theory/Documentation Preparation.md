# Тестирование frontend

### Использование чит-листа
[Чит-лист](/Testing/Documentation/Cheat-List/Cheat-List.md) - список уже готовых проверок, которые можно пробежать за минуту, сравнивая с реализацией, без необходимости составлять отдельную документацию

Например, есть стандартное поле ввода и по постановке оно:
* Обязательное
* Предзаполнено определенными данными
* Имеет ограничение в 150 символов

А по дизайну имеет:
* Лэйбл
* Плейсхолдер

Берется соответствующий чит-лист [поля ввода](/Testing/Documentation/Cheat-List/Input/Input.md) и смотрятся содержащиеся в нем группы:
* ОБЩЕЕ - содержит проверки, характерные для любого типа поля и делится на три подгруппы:
  * ДИЗАЙН - сверка с гайдами дизайнера
  * СОСТОЯНИЕ - различные состояния элемента
  * ДЕЙСТВИЕ - совершаемые над элементом действия
* ТЕКСТОВЫЙ - содержит проверки, характерные только для текстового типа поля
* ЧИСЛОВОЙ - содержит проверки, характерные только для числового типа поля
* ЛЭЙБЛ - содержит проверки, характерные только для лэйбла
* ПЛЕЙСХОЛДЕР - содержит проверки, характерные только для плейсхолдера

Чтобы протестировать реализованное разработчиком, необходимо пройтись по всем проверкам из групп ОБЩЕЕ, ТЕКСТОВЫЙ, ЧИСЛОВОЙ, ЛЭЙБЛ и ПЛЕЙСХОЛДЕР, вынося в чек-лист проверки, описанные в постановке, и отбрасывая нехарактерные для проверяемого поля. Итогом этого станут:
1. Найденные дефекты
2. Записанные вопросы к дизайнеру, аналитику, разработчику
3. Составленный расширенный [чек-лист](/Testing/Documentation/Check-List.md#%D0%B8%D1%81%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5-%D1%87%D0%B5%D0%BA-%D0%BB%D0%B8%D1%81%D1%82%D0%B0)

> [!IMPORTANT]
> При использовании чит-листа необходимо:
> * Определить элементы интерфейса
> * Скомбинировать разные чит-листы и пройти только актуальные для тестируемых элементов проверки
> * В чек-лист вынести только то, что прописано в постановке по тестируемым элементам

### Использование чек-листа
Если чит-листом проверяется дизайн, состояние элементов интерфейса и однообразные взаимодействия над элементами, то в чек-лист вносятся все действия, направленные на проверку условий, описанных в постановке. Для данного примера чек-лист будет выглядеть так:

    Обязательное:
        * При пустом поле > вывод ошибки при сохранении (или (в зависимости от постановки) сразу под полем при снятии фокуса с поля)
    Ограничение количества вводимых символов: 150:
        * Ввод и вставка (Ctrl + V) минимального/максимального количества символов с пробелами и без
              - При ограничении кол-ва символов > вывод ошибки с количеством разрешенных символов
    Предзаполненное определенными данными

> [!IMPORTANT]
> При создании чек-листа в него вносятся любые проверки, описанные в постановке и вышедшие за пределы базового функционала:
> * Валидации элементов
> * Сложная (разветвленная) логика
> * СRUD
> * Иные проверки, пришедшие в голову тестировщику

### Использование тест-кейса
Тест-кейс составляется на базовый функционал со сложной логикой (Create из [CRUD](/Testing/Theory/CRUD.md)), что в дальнейшем позволяет на его основе составлять любые чек-листы, а также позволит использовать его в качестве базового позитивного кейса, в [дымовом тестировании](/Testing/Theory/Types%20Of%20Testing.md#%D0%B4%D1%8B%D0%BC%D0%BE%D0%B2%D0%BE%D0%B5-%D1%82%D0%B5%D1%81%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5-smoke-testing), в [UAT](/Testing/Theory/Types%20Of%20Testing.md#%D0%BF%D1%80%D0%B8%D1%91%D0%BC%D0%BE%D1%87%D0%BD%D0%BE%D0%B5-%D1%82%D0%B5%D1%81%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5-acceptance-testing) и в автоматизации

> [!IMPORTANT]
> Тест-кейс всегда:
> * Пишется для базового функционала, независимо от покрытия чек-листом
> * Задействует максимальное количество сложной логики при создании сущности, вследствие чего, использует максимальное количество данных при проверке (все возможные поля заполнены, чекбоксы установлены, свитчеры включены и т.д.)

### Правила создания документации
1. В документацию вносится логика, описанная в постановке. **Исключение:**
   * Если над элементом не производятся действия (например, поле по умолчанию пустое; свитчер по умолчанию выключен; чекбокс по умолчанию снят и т.д.)
   * Элемент содержит простейшую (единственную) логику (например, крестик/кнопка Закрыть - закрывает окно/форму и больше ничего не делает)
2. Для тестирования frontend использовать связку [чит-лист](/Testing/Documentation/Cheat-List/Cheat-List.md) > [тест-кейс](/Testing/Documentation/Test-Case.md) > [чек-лист](/Testing/Documentation/Check-List.md)
3. Все, что покрывается чек-листами, ими же и остается. **Исключение:**
   * Создание тест-кейса для базового функционала со сложной логикой
