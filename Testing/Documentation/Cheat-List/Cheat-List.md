# Чит-лист
Список универсальных проверок
> [!NOTE]
> В отличие от [чек-листа](/Testing/Documentation/Check-List.md), чит-лист статичен и представляет собой список одних и тех же действий над элементами интерфейса и подходит всем:
> * аналитику при создании постановок
> * дизайнеру, начиная с этапа прототипирования
> * разработчику, чтобы не забыл сверстать
> * тестировщику, чтобы не забыл проверить

### Как пользоваться?
Есть стандартное поле ввода. По постановке оно:
1. обязательное
2. имеет ограничение в 150 букв
По дизайну имеет:
1. лэйбл
2. плейсхолдер

Берется соответствующий чит-лист [поля ввода](/Testing/Documentation/Cheat-List/Input/Input.md) и смотрятся содержащиеся в нем группы:
* ОБЩЕЕ - содержит проверки, характерные для любого типа поля и делится на три подгруппы:
  * ДИЗАЙН - сверка с гайдами дизайнера
  * СОСТОЯНИЕ - различные состояния поля
  * ДЕЙСТВИЕ - совершаемые над полем действия
* ТЕКСТОВЫЙ - содержит проверки, характерные только для текстового типа поля
* ЧИСЛОВОЙ - содержит проверки, характерные только для числового типа поля
* ЛЭЙБЛ - содержит проверки, характерные только для лэйбла
* ПЛЕЙСХОЛДЕР - содержит проверки, характерные только для плейсхолдера

Чтобы протестировать реализованное разработчиком, необходимо забрать актуальные для поля проверки из групп ОБЩЕЕ, ТЕКСТОВЫЙ, ЛЭЙБЛ и ПЛЕЙСХОЛДЕР и отбросить нехарактерные. Чит-лист сам по себе список уже готовых проверок. Можно просто пробежать их за несколько секунд без необходимости составлять документацию. Итогом этого станут:
1. найденные дефекты
2. записанные вопросы к дизайнеру, аналитику, разработчику
3. составленный расширенный чек-лист

Если чит-листом проверяется дизайн, состояние элементов интерфейса и однообразные взаимодействия, то в чек-лист вносятся все действия, направленные на проверку условий, описанных в постановке. Для данного примера составление чек-листа из чит-листа будет выглядеть так:
* Обязательное
  * При пустом поле > вывод ошибки при сохранении (или (в зависимости от постановки) сразу под полем при снятии фокуса с поля)
* Ограничение количества букв: 150
  * При превышении > вывод ошибки с количеством разрешенных символов

Добавление в чек-лист остальных проверок, зависит от правил составления расширенного [чек-листа](/Testing/Documentation/Check-List.md)

> [!IMPORTANT]
> Резюме. При проверке по чит-листам необходимо:
> 1. Определить элемент интерфейса (а для полей ввода еще и его тип)
> 2. Скомбинировать разные чит-листы и пройти только актуальные для тестируемого элемента проверки
> 3. В чек-лист вынести только то, что прописано в постановке по тестируемому элементу
  > 3.1 При этом в чек-лист нет необходимости заносить проверки элементов, имеющих простейшую логику: например, крестик или кнопка Закрыть - просто закрывают окно/форму. Но если при нажатии на крестик/кнопку Закрыть должно всплывать модальное окно (например, для сохранения данных) - это уже необходимо описать в чек-листе, так как такая логика является разветвленной (срабатывает по определенным правилам) и точно должна быть описана в постановке
