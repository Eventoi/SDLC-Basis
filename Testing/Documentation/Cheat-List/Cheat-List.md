# Чит-лист
Список универсальных проверок
> [!NOTE]
> В отличие от [чек-листа](/Testing/Documentation/Check-List.md), чит-лист статичен и представляет собой список одних и тех же действий над элементами интерфейса и подходит всем:
> * аналитику при создании постановок
> * дизайнеру, начиная с этапа прототипирования
> * разработчику, чтобы не забыл сверстать
> * тестировщику, чтобы не забыл проверить

### Как пользоваться?
Возьмем стандартное поле ввода. По постановке оно:
1. обязательное
2. имеет ограничение в 150 букв

Берем соответствующий чит-лист [поля ввода](/Testing/Documentation/Cheat-List/Input/Input.md) и отбрасываем проверки, нехарактерные для этого поля, выбирая актуальные из групп:
* ОБЩЕЕ - содержит проверки, характерные для любого типа поля и делится на три подгруппы:
  * ДИЗАЙН - сверка с гайдами дизайнера
  * СОСТОЯНИЕ - состояние поля по умолчанию
  * ДЕЙСТВИЕ - совершаемые с полем действия
* ТЕКСТОВЫЙ - содержит проверки, характерные только для текстового типа поля
* ЧИСЛОВОЙ - содержит проверки, характерные только для числового типа поля
Остальные группы - это проверки элементов самого поля, которые могут отсутствовать

В данном примере необходимо забрать актуальные для поля проверки из групп ОБЩЕЕ и ТЕКСТОВЫЙ. Остальные - при необходимости. Так как чит-лист это уже список готовых проверок, то можно просто пробежать их за несколько секунд. Итогом этого станут:
1. найденные дефекты
2. записанные вопросы к дизайнеру, аналитику, разработчику
3. составленный расширенный [чек-лист](/Testing/Documentation/Check-List.md)

Если чит-листом мы проверяем дизайн, состояние элементов интерфейса и однообразные взаимодействия, то в чек-лист выносятся все действия, направленные на проверку правил, описанных в постановке. Для данного примера чек-лист будет выглядеть так:
* Обязательное
  * При пустом поле: вывод ошибки при сохранении (или, в зависимости от постановки, сразу под полем при снятии фокуса с поля)
* Ограничение количества букв: 150
  * При превышении: вывод ошибки с количеством разрешенных символов
Добавление остальных проверок зависит от фантазии и насмотренности тестировщика

> [!IMPORTANT]
> Резюме. При создании чит- и чек-листов необходимо:
> 1. Выделить тип каждого свёрстанного элемента
> 2. Скомбинировать разные чит-листы и пройти только актуальные для проверяемого элемента проверки
> 3. В чек-лист вынести только то, что прописано в постановке про каждый элемент
